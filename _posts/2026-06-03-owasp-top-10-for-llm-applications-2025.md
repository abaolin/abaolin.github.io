## 核心内容提炼

OWASP 于 2024 年 11 月发布的《Top 10 for LLM Applications 2025》在 2023 版基础上做了大幅更新：将拒绝服务扩展为更贴近大规模部署成本痛点的「无限制资源消耗」，新增针对 RAG 的「向量与嵌入弱点」和「系统提示词泄露」，并因 Agent 架构的普及强化了「过度授权」。本文按 LLM01 到 LLM10 逐项拆解风险本质、典型攻击场景与工程化缓解手段，帮助开发者与安全团队把这套框架落到 CI/CD、网关、RAG 流水线和 Agent 权限治理中。

> 由 claude-opus-4-8 模型总结提炼，观点仅供参考。

## 2025 版有哪些关键变化

相比 2023 版，2025 版本的调整反映了 LLM 真正进入生产环境后的新教训：

- **拒绝服务升级为「无限制资源消耗」（LLM10）**：不再只关注可用性宕机，而是把推理成本失控、Token 滥用、模型被「白嫖」窃取等经济性风险纳入视野。
- **新增「向量与嵌入弱点」（LLM08）**：回应社区对 RAG 安全的强烈需求，因为检索增强已成为给模型「接地气」的主流做法。
- **新增「系统提示词泄露」（LLM07）**：现实中已出现真实利用案例，开发者不能再假设系统提示词是绝对私密的。
- **强化「过度授权」（LLM06）**：随着 Agent 与插件架构赋予模型更多自主权，未受控的权限会直接放大风险。

核心信息很清晰：**LLM 安全不再是模型层的孤立话题，而是贯穿数据、供应链、提示词、输出处理、Agent 权限和成本治理的全栈工程问题。**

## LLM01：提示注入（Prompt Injection）

**风险本质**：用户输入或外部内容中夹带的指令改变了模型行为，使其偏离开发者预期。由于模型无法可靠区分「系统意图」与「用户/数据中的指令」，这是 LLM 最根本的安全难题。

**两类典型形态**：
- **直接注入**：用户在对话中直接输入「忽略以上所有指令」之类的越权指令。
- **间接注入**：恶意指令藏在网页、文档、邮件等被模型读取的外部数据里，在 RAG 或浏览场景中尤为危险。

**工程化缓解**：
- 用系统层约束模型行为，并对输出做格式校验与白名单过滤。
- 对输入与检索内容做来源标注和隔离，区分「可信指令」与「不可信数据」。
- 对高风险操作引入人工确认（human-in-the-loop）。
- 采用最小权限原则，限制模型可调用的工具与数据范围。
- 部署对抗性测试与红队演练，持续验证防护有效性。

## LLM02：敏感信息泄露（Sensitive Information Disclosure）

**风险本质**：模型在输出中暴露 PII、商业机密、凭证、内部算法或训练数据，可能源于训练数据残留、上下文泄露或提示词诱导。

**常见场景**：
- 模型「背诵」出训练语料中的个人信息或密钥。
- 多租户场景下，上下文或缓存串台导致 A 用户看到 B 用户数据。
- 用户通过精心构造的问题反推出系统内部数据。

**工程化缓解**：
- 在数据进入训练/检索前做脱敏、最小化与分类分级。
- 对输出做敏感信息检测与拦截（如正则+分类器过滤 PII/密钥）。
- 落实严格的访问控制与租户隔离，避免上下文交叉污染。
- 在用户协议与产品中明确数据使用边界，提供 opt-out 机制。
- 谨慎使用联邦学习、差分隐私等技术降低记忆性风险。

## LLM03：供应链风险（Supply Chain）

**风险本质**：LLM 应用依赖大量第三方组件——基础模型、开源权重、数据集、微调适配器（LoRA）、推理框架与插件，任何一环被污染或失陷都会传导到整个系统。

**典型风险**：
- 从公开仓库下载被植入后门的模型或权重文件。
- 依赖的开源库或 LoRA 适配器存在恶意代码或漏洞。
- 模型许可证不合规、数据来源不可追溯。
- 第三方 API/插件供应商被攻破。

**工程化缓解**：
- 维护 AI 物料清单（AI-BOM），追踪模型、数据集与依赖来源。
- 对模型与权重做完整性校验（签名、哈希），优先使用可信来源。
- 引入 SCA/漏洞扫描，定期审计第三方组件。
- 对外部模型在沙箱中评测后再上线，并做异常行为监控。
- 明确许可证合规要求，纳入采购与法务流程。

## LLM04：数据与模型投毒（Data and Model Poisoning）

**风险本质**：攻击者在预训练、微调或嵌入阶段注入恶意数据，植入后门、偏见或可被触发的有害行为，破坏模型完整性。

**常见场景**：
- 污染公开数据集，使模型在特定触发词下产出恶意输出。
- 微调数据中夹带偏见或错误知识。
- 在持续学习/在线反馈机制中投喂误导样本。

**工程化缓解**：
- 严格审查与验证训练数据来源，建立数据溯源与版本管理。
- 使用异常检测识别可疑样本，对数据做清洗与去毒。
- 通过对抗训练、鲁棒性评测增强模型抗投毒能力。
- 隔离与监控用户反馈数据，避免直接污染再训练流程。
- 在部署前后做行为基线对比，发现后门触发迹象。

## LLM05：不当的输出处理（Improper Output Handling）

**风险本质**：下游系统盲目信任并直接使用模型输出，导致 XSS、SQL 注入、命令执行、SSRF 等传统漏洞被「模型生成」的内容重新带入。这本质上是「把 LLM 输出当作可信代码/指令」的反模式。

**常见场景**：
- 模型生成的 HTML/JS 直接渲染到前端，造成 XSS。
- 模型生成的 SQL 或 Shell 命令未经校验直接执行。
- 模型输出被用于拼接 URL 发起内网请求，造成 SSRF。

**工程化缓解**：
- **将模型输出视为不可信用户输入**，统一做编码、转义与参数化。
- 对下游调用做严格的 schema 校验与白名单约束。
- 遵循最小权限，限制输出可触发的操作范围。
- 对生成代码/命令引入沙箱执行与人工审核。
- 在前端输出处统一做内容安全策略（CSP）与转义。

## LLM06：过度授权（Excessive Agency）

**风险本质**：当 LLM 作为 Agent 调用工具、API 或执行操作时，过多的功能、权限或自治度会让一次错误判断或被注入的指令演变成真实破坏。2025 版因 Agent 架构普及而显著强化此项。

**风险三要素**：
- **过多功能**：插件/工具暴露了超出业务所需的能力。
- **过高权限**：模型以高权限身份访问数据库、文件或外部系统。
- **过度自治**：高风险动作无需人工确认即可执行。

**工程化缓解**：
- 最小化工具集，只暴露完成任务必需的功能与参数。
- 以最小权限令牌调用下游，按用户身份做权限继承而非共享高权账号。
- 对删除、转账、发邮件等高影响动作强制人工审批。
- 记录完整的操作审计日志，支持事后追溯与限流熔断。
- 在 Agent 编排层做策略校验（policy enforcement）与速率控制。

## LLM07：系统提示词泄露（System Prompt Leakage）

**风险本质**：开发者常把规则、凭证、内部逻辑甚至密钥写进系统提示词，并误以为它们对用户不可见。2025 版明确指出：**绝不能把系统提示词当作安全边界**，因为它可能被诱导泄露。

**常见风险**：
- 系统提示词中硬编码 API Key、数据库连接串等敏感信息。
- 提示词暴露了内部业务规则、过滤逻辑，便于攻击者绕过。
- 泄露的提示词揭示了权限结构，为进一步攻击提供路线图。

**工程化缓解**：
- **绝不在提示词中存放凭证或敏感配置**，改用安全的密钥管理服务。
- 把真正的安全管控放在应用层（鉴权、授权、过滤），而非依赖提示词保密。
- 假设提示词随时可能泄露，以此为前提做威胁建模。
- 对关键决策引入独立的外部校验，不让模型「自证清白」。

## LLM08：向量与嵌入弱点（Vector and Embedding Weaknesses）

**风险本质**：RAG 已成主流，但向量数据库与嵌入流程本身引入了新攻击面——检索内容可被污染、跨租户数据可能泄露、嵌入可被反演还原出原始信息。

**常见风险**：
- **嵌入反演**：从向量反推还原原始敏感文本。
- **数据投毒**：向知识库注入恶意文档，影响检索结果与模型回答（间接注入的温床）。
- **多租户串台**：向量库隔离不当导致 A 租户检索到 B 租户数据。
- **过期/冲突知识**：检索到陈旧或矛盾内容，污染输出。

**工程化缓解**：
- 对向量库实施严格的访问控制与租户隔离（按命名空间/索引分区）。
- 对入库文档做来源校验、权限标注与内容审查，防止知识库被投毒。
- 对检索结果做相关性与可信度过滤，并标注来源供模型与用户判断。
- 加密敏感嵌入，评估嵌入反演风险，必要时降维或脱敏。
- 建立知识库更新与版本治理，及时清理过期内容。

## LLM09：错误信息（Misinformation）

**风险本质**：模型可能自信地生成虚假、过时或误导性内容（即「幻觉」），用户的过度信任会放大其危害，在医疗、法律、金融等场景尤其危险。

**常见风险**：
- 事实性幻觉：编造不存在的引用、数据或 API。
- 过时知识：基于训练截止前的信息给出错误结论。
- 过度依赖：用户或下游系统未经核实直接采纳模型输出。
- 不安全代码建议：生成引用了虚构或有漏洞依赖的代码（供应链风险联动）。

**工程化缓解**：
- 用 RAG 把回答接地到权威、可溯源的知识库，并附带引用。
- 对高风险领域引入人工复核与专家校验流程。
- 在产品 UI 中明确提示「内容可能有误」，降低过度信任。
- 对生成代码做依赖校验与安全扫描。
- 通过自洽性检查、交叉验证等手段降低幻觉率，并持续评测准确性。

## LLM10：无限制资源消耗（Unbounded Consumption）

**风险本质**：2025 版将「拒绝服务」扩展为这一项，既涵盖可用性攻击，也涵盖**经济性攻击**——攻击者通过海量或超长请求拉爆推理成本（Denial of Wallet），甚至通过大量查询窃取/蒸馏模型能力。

**常见场景**：
- 构造超长上下文或递归请求，耗尽算力与预算。
- 高频调用导致服务降级或成本激增。
- 通过系统化查询做模型萃取，复制出近似模型（知识产权风险）。

**工程化缓解**：
- 对输入长度、并发与频率做严格限流与配额管理。
- 设置 Token/成本预算告警与自动熔断，监控异常消耗模式。
- 对单用户/单租户做速率与资源隔离，防止「白嫖」。
- 对疑似模型萃取的查询模式做检测与限制。
- 用缓存、批处理、模型分级路由优化成本，并做容量规划与压测。

## 落地建议：把 Top 10 接入威胁建模与研发流程

OWASP 在附录中给出了 LLM 应用架构与威胁建模指引。要把这套框架真正用起来，建议：

- **画出数据流与信任边界**：明确用户输入、外部数据、RAG 知识库、Agent 工具调用各自的可信级别，针对每条边界对照 Top 10 排查。
- **把控制点分层落地**：网关层做输入/输出过滤与限流（LLM01/05/10），数据层做脱敏与溯源（LLM02/03/04/08），Agent 层做权限与审批（LLM06），密钥与配置层做隔离（LLM07）。
- **建立持续评测**：将红队、对抗测试、幻觉评测、成本监控纳入 CI/CD 与线上观测。
- **以「不可信」为默认假设**：模型输出、系统提示词、外部检索内容都按不可信处理，安全边界放在应用层而非模型自觉。

这份清单是开源社区的集体经验产物，会随技术演进持续更新。把它作为团队的安全基线 checklist，能让 LLM 应用从原型走向生产时少踩很多坑。
